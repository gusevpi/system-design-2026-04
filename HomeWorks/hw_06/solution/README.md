> Данная работа выполнена по мотивам реальной системы в промышленной эксплуатации, усеченная по узлам, с учетом ограничений госсектора.

## Выбранная тема

_"Система хранения, обработки и предоставления данных о гражданах, полученных от ОИВ и ФОИВ"_

---
## 1. Требования

- **Функциональные** — scope проекта:
   - Интеграция с ФОИВ/ОИВ:
     - ЕРН (SOAP)
     - ФИАС (получение архивов через HTTPS)
     - мЕРН (SOAP)
     - НСУД (REST + асинхронный ответ в очередь)
     - ДСЗН (очередь + DLQ)
     - ЕМИАС (SOAP + ответ в очередь).
   - Ведение мастер-данных гражданина (дедупликация, обновление).
   - Учёт МСП, ЛК и транзакций(фактов оказания мер поддержки)
   - Формирование витрин данных
   - Отчётность: отдельный сервис с фронтендом для внешних пользователей (авторизация логин/пароль).
   - Аудит: кто, когда, из какого ОИВ, что изменил.
   - Обработка лимитов на количество обращений в день

- **Нефункциональные** — конкретные цифры:
   - Граждане: 30 млн (10 млн активных), прогноз на 3 года — ~45 млн.
   - МСП и ЛК: 500 млн исторических, прогноз — ~750 млн.
   - Транзакции: 5 млрд, прогноз — ~7.5 млрд (прирост 1.5 млн/день).
   - RPS чтения: 100, 10 000 (пик).
   - RPS записи: 10, 100 (пик).
   - Latency: поиск по ID/СНИЛС ≤ 100 мс; по ФИО ≤ 500 мс.
   - SLA: 99.95%.
   - RPO = 15 мин
   - RTO = 1 час.

- **Риски и ограничения:**
  - Асинхронные ответы (НСУД, ДСЗН, ЕМИАС) — задержка актуализации до 5 суток.
  - Отказ внешних сервисов. Как недоступность сервисов, так и многомесячное отсутствие консьюмеров у потребителей из-за тех. сбоев
  - Отсутствие перспектив внедрения OLAP-хранилища (ClickHouse), пока есть только PostgreSQL.

- **Backlog** — что не входит в scope:
   - Интерфейс бизнес администратора для управления и корректировки данных гражданина.
   - Полноценный DWH.

## 2. Концептуальная архитектура

- **Схема C4**
  - Context
    - [Context diagram](diagrams/Context Diagram.md)
  - Container
    - [Container diagram](diagrams/Container Diagram.md)

- **Описание компонентов:**
    - **API Gateway** — Корневой многофункциональный шлюз. Осуществляет маршрутизацию, rate limiting, валидацию JWT.
    - **Internal Ingestion Service** — Вычитка из внешнего Artemis сообщений и событий от ЕРН, мЕРН, НСУД, ЕМИАС, ФИАС, валидация, преобразование(при необходимости), публикация во внутренний Artemis.
    - **Citizen Profile Service** — Управление мастер-данными граждан.
    - **MSP Service** — Управление мерами поддержкит.
    - **LK Service** — Управление льготами.
    - **Transaction Service** — Высоконагруженная обработка транзакций.
    - **Data Mart Builder** — Наполнение витрин по событиям.
    - **Reporting Service** — фронтенд для формирования и отображения отчётов.
    - **Artemis External** — брокер для внешних интеграций. Отдельный для изоляции. Располагается в отдельном сегменте сети
    - **Artemis Internal** — брокер для внутренних взаимодействий.
    - **PostgreSQL 19 (Master)** — База данных. Мастер.
    - **PostgreSQL 19 (Replica)** — 1 нода, read-only. Используется для репликации данных. Также используется для наплнения БД витрин(Data Marts).
    - **PostgreSQL 19 (Data Marts)** — 1 нода, read-only для витрин и отчётов.
    - **Redis** — Кэш актуальных профилей граждан, их МСП и ЛК (TTL 15 мин).

- **Обоснование архитектурного стиля:**
    - SOA с микросервисными паттернами. Исторически сложилось, редкие релизы, маленькая команда. Нет смысла в микросервисной архитектуре.
    - Два брокера Artemis обеспечивают изоляцию внешних и внутренних потоков. Это исходить из требований к гос. ИС
    - Витрины данных отделяют аналитику от OLTP. Хранят предварительно подготовленные данные для отчетов в денормализованном виде
    - Сотрудники ОИВ работают только с витринами (безопасность + разгрузка мастер-БД).

- **ADR для 2–3 ключевых решений:**
    - **ADR 1: Два инстанса Artemis (External / Internal).** Изоляция отказов: переполнение внешней очереди не блокирует внутренние сервисы.
    - **ADR 2: Витрины на Read-реплике PostgreSQL 19.** Разделение OLTP и OLAP; наполнение по событиям через Data Mart Builder.
    - **ADR 3: Партиционирование.** `transactions` — по месяцам (Range); `citizens` — по хэшу `citizen_id`.

- **Пользователи и внешние интеграции:**
    - **Пользователи:** сотрудники различных ОИВ (витрины + отчёты), администраторы.
    - **Авторизация:** via СУДИР (логин/пароль), Mos.ru (токен); для фронта отчётов — логин/пароль как исключительный вариант.
    - **ФОИВ:** ЕРН (SOAP), ФИАС (HTTPS, получение ежемесячно архивов с актуальными данными).
    - **ОИВ:** мЕРН (SOAP), НСУД (REST синх. + очередь асинх.), ДСЗН (SOAP + очередь с DLQ), ЕМИАС (SOAP + очередь).

## 3. Сайзинг
- RPS чтения: 10 000; RPS записи: 17 (средний) / 100 (пик).
- Хранилище (с прогнозом на 3 года):
    - Citizen: 45 млн × 2 КБ ≈ 90 ГБ.
    - MSP/LK: 750 млн × 1 КБ ≈ 750 ГБ.
    - Transactions: 7.5 млрд × 0.5 КБ ≈ 3.75 ТБ.
    - Аудит: 7.5 млрд × 0.5 КБ ≈ 3.75 ТБ.
    - Витрины: ~1 ТБ.
    - **Итого:** ~9.3 ТБ сырых данных (~12 ТБ с индексами).
- Ресурсы (K8s, физические серверы):
    - API Gateway + Сервисы: 3 физических сервера (2×16 vCPU, 64 GB RAM каждый).
    - PostgreSQL Master: 1 сервер (16 vCPU, 64 GB RAM, NVMe SSD).
    - PostgreSQL Replica: 1 сервер (16 vCPU, 64 GB RAM, NVMe SSD).
    - PostgreSQL Data Marts: 1 сервер (8 vCPU, 32 GB RAM, SSD).
    - Redis: 1 сервер (8 vCPU, 32 GB RAM).
    - Artemis External + Internal: 2 сервера (4 vCPU, 16 GB RAM).
    - Airflow + Reporting: 1 сервер (8 vCPU, 32 GB RAM).

---
- **Расчёт стоимости (On-Premise, USD, горизонт 3 года):**

  **Методика:** CAPEX (железо) + OPEX (электричество, стойки, персонал) / 36 месяцев

  **CAPEX (единовременно):**

  | Компонент | Конфигурация | Ориентир цены (USD)                   |
    |---|---|---------------------------------------|
  | Серверы приложений (3 шт.) | 2×16c/64GB, SSD | 3 × $6,000 = **$18,000**            |
  | Серверы БД (3 шт.) | 16c/64GB, NVMe | 2 × $8,000 + 1 × $6,000 = **$22,000**|
  | Серверы Redis/Artemis/Airflow (4 шт.) | 8c/32GB, SSD | 4 × $3,500 = **$14,000**              |
  | СХД (12 ТБ usable, RAID) | NVMe/SSD | **$10,000**                           |
  | Сетевое оборудование | 2 коммутатора 10G, резерв | **$5,000**                            |
  | **Итого CAPEX** | | **≈ $69,000**                         |

  **OPEX (ежемесячно):**

  | Статья | Расчёт | Стоимость/мес (USD) |
    |---|---|---|
  | Электричество | ~5 кВт × 720 ч × $0.08/кВт·ч | **$288** |
  | Стойки (2 стойки, colocation) | $500/стойка | **$1,000** |
  | Лицензии ОС | $0 (open source) | **$0** |
  | PostgreSQL | Open Source | **$0** |
  | **Персонал (0.5 FTE DevOps + 0.5 FTE SRE, с налогами)** | ($2,500 × 0.5 + $3,000 × 0.5) × 2 | **$5,500** |
  | **Итого OPEX** | | **≈ $6,788/мес** |

  **Совокупная стоимость за 3 года:**
    - CAPEX: $69,000
    - OPEX: $6,788 × 36 = $244,368
    - **Итого TCO (3 года): ≈ $313,368**
    - **Среднемесячная стоимость: ≈ $8,705/мес**

## 4. Хранение данных
- СУБД: PostgreSQL 19
  - Обоснование: Транзакционные данные (профили граждан, МСП, ЛК, транзакции) требуют строгой консистентности. PostgreSQL обеспечивает надёжность, поддержку сложных запросов, партиционирование и расширяемость. 
  - Почему не альтернативы:
    - MySQL — слабее в сложных аналитических запросах и партиционировании; меньше возможностей для расширения. 
    - Oracle / MS SQL — дорогие лицензии
    - ClickHouse - отлично для OLAP, но не подходит для OLTP (нет транзакций).

- Партиционирование: `transactions` — по месяцам; `citizens` — по хэшу.
- Витрины: отдельная БД `PG_DM`, наполнение через Apache Airflow из `PG_Replica`.
- Кэш: Redis (Cache-Aside, TTL 15 мин).

## 9. Тестирование
    - План нагрузочного тестирования
    - Chaos-эксперименты
- Инструмент: Apache JMeter.
- Модули: API Gateway, Citizen Profile Service (gRPC), Reporting Service.
- Сценарии:
  1. **«Поиск в витринах»** — 10 RPS (GET), ramp-up 10 мин; цель p95 < 7 с; перцентили 50/90/95/99.
  2. **«Массовый приём транзакций»** — 100 RPS (POST), 30 мин; контроль роста DLQ.
  3. **«Построение отчётов»** — 5 одновременных пользователей; проверка, что отчёты на реплике не влияют на OLTP.
- Методика: step-up до деградации (p95 > 300 мс/30 с или error rate > 1%); фиксация точки отказа.

### Chaos-эксперименты
| № | Эксперимент | Действие                                           |
|---|---|----------------------------------------------------|
| 1 | **Отказ пода API Gateway** | Удаляем 1 из 3 подов Gateway                       |
| 2 | **Отказ пода Citizen Profile Service** | Удаляем 1 под Profile Service                             |
| 3 | **Отказ ноды PostgreSQL Master** | Останавливаем мастер-БД (имитация падения сервера) |
| 4 | **Задержка сети между Gateway и Artemis External** | Добавляем 500 мс задержки через `tc`               |
| 5 | **Переполнение DLQ (ДСЗН)** | Отправляем 10 000 «битых» сообщений в очередь ДСЗН |
| 6 | **Отказ Redis** | Останавливаем Redis                                |
| 7 | **Отказ Airflow** | Блокируем запуск DAG                               |
| 8 | **Потеря связи с внешней системой (ЕМИАС)** | Блокируем исходящий трафик к ЕМИАС                 |
| 9 | **Отказ 2 из 3 подов Artemis External** | Удаляем 2 пода брокера                             |
| 10 | **CPU-стресс на ноде PostgreSQL** | Запускаем `stress-ng --cpu 16` на ноде БД          |
