## 0. Контекст системы
Сервис такси связывает пассажиров с водителями в реальном времени:
принимает заказ, подбирает ближайшего подходящего водителя, строит маршрут, рассчитывает стоимость (включая динамическое ценообразование) и проводит оплату.

### Основные акторы:
* Пассажир - заказывает поездку, отслеживает водителя, оплачивает
* Водитель - получает заказы, подтверждает, выполняет поездку
* Оператор поддержки - разбирает проблемные ситуации
* Внешние системы — платёжные шлюзы, картографические провайдеры

### Масштаб:
* Миллионы пользователей (пассажиры + водители)
* Десятки тысяч одновременных поездок в пике
* RPS на геообновления: тысячи/сек


## 1. Компоненты

_Основные сервисы и их ответственности (5–10 компонентов)._

* API Gateway
  * Балансировщик + шлюз.
  * Единая точка входа, аутентификация, rate limiting, маршрутизация м.б.
  * Stateless
* Geo
  * Сервис + in-memory БД
  * Принимает координаты водителей и пассажиров, пространственные запросы «кто рядом»
  * Stateful
* Matching
  * Сервис
  * Выбора водителя для заказа
  * Stateless
* Pricing
  * Сервис + кэш тарифов
  * Ценообразование, тарифы
  * Stateless
* Trip
  * Сервис+ БД
  * Отвечает за жизненный цикл поездки, историю поездок. Он же является сервисом заказа, который создастся и будет менять статус.
  * Stateful
* Notification
  * Сервис уведомлений. Там же пока Push компонент водителям/пассажирам
  * Stateless
* Routing
  * Сервис марщрутов
  * Отвечает за построение маршрутов
  * Stateless
* Payment
  * Сервис + БД
  * Сервис оплаты. Привязка карт, списания, возвраты
  * Stateful
* Kafka/Event Bus
  * Очередь/шина событий для взаимодействия сервисов
* Analytics
  * Сервис анализа, дашбордов, отчетов
  * Stateless

## 2. Потоки данных

### Сценарий 1: Пассажир вызывает такси

#### Путь запроса:
Rider App → API Gateway → Trip Service → Pricing Service → Trip Service (создание заказа) → Matching Service → Geo Service → Matching Service → Notification Service → Driver App → Trip Service → Rider App.

#### Порядок и характер взаимодействия:
* Пассажир отправляет запрос с координатами и тарифом — синхронно через API Gateway.
* API Gateway аутентифицирует и маршрутизирует в Trip Service.
* Trip Service вызывает Pricing Service для получения предварительной стоимости — синхронно.
* Trip Service создаёт заказ с начальным статусом, фиксирует идемпотентный ключ — запись в БД.
* Trip Service вызывает Matching Service для подбора водителя — синхронно.
* Matching Service запрашивает Geo Service о водителях в радиусе — синхронно.
* Matching выбирает кандидата и передаёт в Notification Service — асинхронно.
* Notification шлёт push водителю — асинхронно.
* Водитель принимает → Notification публикует событие → Trip Service обновляет статус → push пассажиру.

#### При сбое:
* Pricing недоступен → заказ создаётся с базовым тарифом (fallback), цена уточняется позже.
* Geo недоступен → Matching использует fallback-кэш последних координат или возвращает «попробуйте позже».
* Водитель не ответил за таймаут → Notification эскалирует следующему кандидату, увеличивается счётчик попыток в Trip Service.
* Trip DB недоступна → запрос отклоняется (нельзя создать заказ без фиксации), retry на клиенте.
* Kafka недоступна → события буферизуются в outbox-таблице Trip, отправятся позже.

### Сценарий 2: Водитель транслирует свою геолокацию

#### Путь запроса:
Driver App → API Gateway → Geo Service → in-memory геоиндекс → Kafka → Analytics; Geo Service → Routing Service (для отображения на карте).

#### Порядок и характер взаимодействия:
* Водитель отправляет координаты каждые 2–4 секунды — синхронно через API Gateway.
* Geo Service обновляет in-memory индекс — запись в память.
* Geo Service публикует событие — асинхронно.
* Analytics потребляет события для прогноза спроса и отчётов — асинхронно.
* Routing Service читает актуальные координаты для отображения пассажиру — синхронно (чтение из Geo).

#### При сбое:
* Сеть пропала у водителя → клиент буферизует точки офлайн, отправляет пачкой при восстановлении.
* Geo Service перезапустился → индекс восстанавливается replay'ем последних событий из Kafka.
* Kafka недоступна → Geo продолжает писать в память, события буферизуются локально; аналитика догоняет постфактум.
* API Gateway перегружен → rate limiting отсекает часть геоточек, частота обработки снижается адаптивно.

### Сценарий 3: Завершение поездки

#### Путь запроса:
Driver App → API Gateway → Trip Service → Pricing Service (финальный расчёт) → Payment Service → Trip Service → Kafka → Rider App (чек) + Kafka → Analytics.

#### Порядок и характер взаимодействия:
* Водитель завершает поездку — синхронно через API Gateway.
* Trip Service фиксирует статус, считает финальные метрики — запись в БД.
* Trip Service вызывает Pricing Service за финальной суммой — синхронно.
* Trip Service вызывает Payment Service для списания — синхронно с идемпотентным ключом.
* Payment Service списывает через внешний шлюз — синхронно (с retry).
* Trip Service публикует событие — асинхронно.
* Analytics потребляет событие для отчётов и дашбордов — асинхронно.
* Пассажиру уходит push с чеком через Notification — асинхронно.

#### При сбое:
* Payment недоступен → Trip сохраняет состояние, retry с идемпотентным ключом; пассажир видит «оплата обрабатывается».
* Pricing недоступен → используется предварительная цена из заказа, финальный пересчёт откладывается.
* Kafka недоступна → Trip пишет событие в outbox-таблицу, отправит позже.
* Notification недоступен → чек сохраняется в Trip, пассажир увидит его при следующем открытии приложения.
